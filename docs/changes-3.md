## 1. 差分の整理

### ① 共有旅の位置づけ

| | これまで | ご希望 |
| --- | --- | --- |
| 共有旅の扱い | 「旅行の種類」のひとつ。個人の記録の一部 | **独立したアプリ空間**（旅ワークスペース） |
| ホーム | 一人旅も共有旅もまとめて表示 | 選んだ旅だけを表示 |
| 日本地図 | 見えるすべての記録を合算して色付け | **その旅の記録だけ**で色付け |
| 記録・スポット | すべて混在 | その旅だけ |
| 切り替え | なし | 自分の旅 / 共有旅一覧から選ぶ |

**いちばん大きな差分は集計です。** これまで地図の色分けは `area_stats()` が
「RLS で見えるすべての訪問記録」を集計していたため、共有旅に参加した瞬間に
自分の地図の色が増えてしまう作りでした。ここを旅行単位で絞り込む必要があります。

### ② 地図遷移

| | これまで | ご希望 |
| --- | --- | --- |
| 都道府県を開いたあと | 市区町村の**一覧**（代表地点を点で並べた地図と切り替え） | **境界付きの市区町村地図** |
| 地図と一覧の関係 | 「地図」「一覧」の切り替え式 | **上に地図・下に検索＋一覧**のハイブリッド |
| 市区町村の色 | 訪問済み / 未訪問の2段階 | 2段階＋**将来は訪問回数・お気に入り数で濃淡** |

これまでは市区町村の境界データを持っていなかったため、代表座標を点で並べた
配置図でした。境界付きの地図にするには、市区町村の境界データが新たに必要です。

## 2. 影響範囲

### 画面

| 画面 | 影響 |
| --- | --- |
| ホーム `/home` | ワークスペースごとの表示に変更。共有旅一覧から切替 |
| 日本地図 `/map` | その旅の記録だけで色分け。いまの旅を表示 |
| 地方地図 `/map/[region]` | 同上 |
| **都道府県 `/map/[region]/[pref]`** | **境界付き地図＋検索＋一覧のハイブリッドに作り直し** |
| 市区町村 `…/[muni]` | スポット一覧をその旅の分だけに |
| 記録 `/records` | その旅の分だけに。一人旅／共有旅の絞り込みは不要になり非表示 |
| 追加 `/add` | 旅行の選択肢をその旅の分だけに |
| 訪問履歴の追加・編集 | 同上 |
| スポット詳細 `/spots/[id]` | 訪問履歴をその旅の分だけに |
| **旅を選ぶ `/workspaces`（新規）** | 自分の旅・共有旅一覧 |
| マイページ | ここだけは**全体の合計**を出す（アカウント全体の記録のため） |

### データ構造

- **テーブルの追加・変更はありません。** 既存の `trips` / `trip_members` /
  `visit_records` で表現できます。
  - 自分の旅 = 自分が作成した `trip_type = 'solo'` の旅行すべて
  - 共有旅① = `trip_type = 'shared'` の旅行ひとつ
- 開いているワークスペースは **Cookie**（`odekake-workspace`）に持ちます。
  URL を変えないため、既存の画面構成をそのまま使えます。
- 市区町村の境界データを追加しました（`src/lib/geo/municipality-paths/`）。
  都道府県ごとに分割し、サーバー側でその県の分だけ読み込みます。

### API（RPC）

- `area_stats()` … **旅行で絞り込めるように引数を追加**しました。
  引数なしの呼び出しはこれまでどおり動きます（後方互換）。
  あわせて、将来の濃淡表示のために `favorite_count` を返すようにしました。
- そのほかの RPC（`join_trip_by_code` / `delete_own_account`）は変更ありません。

### RLS

**変更はありません。**

ワークスペースの分離は「RLS が許可している範囲を、アプリ側でさらに絞り込む」
仕組みです。RLS はこれまでどおり「参加していない旅行は見えない」を担保し、
ワークスペースは「参加している旅行のうち、いま見る範囲」を決めます。

- `area_stats()` は `security invoker` のままなので、
  他人の旅行 ID を渡しても RLS により1行も返りません
  （`supabase/tests/01_rls.test.sql` で確認しています）。
- ワークスペースの切り替えは、`trips` を1件読めるかどうかで検証しています。
  参加していない旅行 ID を指定しても、RLS により取得できず自分の旅へ戻ります。

## 3. 実装内容

### 3-1. 旅ワークスペース

```
自分の旅        … 自分がつくった一人旅すべて
共有旅①②③…    … 参加している共有旅ひとつずつ
```

- `src/lib/data/workspace.ts` … いまのワークスペースの解決と一覧
- `src/app/actions/workspace.ts` … 切り替え（Cookie の保存）
- `/workspaces` … 旅を選ぶ画面（参加人数つき）
- ホームの上部と、地図・記録の先頭に、いまの旅と切替への導線を置きました

**地図の分離**は `loadAreaIndex(supabase, tripIds)` に集約しています。
共有旅を新しくつくった直後は記録が0件なので、日本地図はすべて未訪問から始まります。
自分の旅や他の共有旅の記録は合算されません。

旅行の作成・参加・退出・削除では、開くべき空間が変わるため自動で切り替えます。

| 操作 | 切り替え先 |
| --- | --- |
| 共有旅をつくる | その共有旅 |
| 招待コードで参加する | 参加した共有旅 |
| 一人旅をつくる | 自分の旅 |
| 共有旅から退出・削除する | 自分の旅 |

### 3-2. 地図遷移

```
日本地図 → 地方地図 → 都道府県地図（市区町村の境界） → 市区町村詳細（スポット一覧）
```

都道府県の画面は、上に地図・下に検索と一覧を並べたハイブリッド構成です。
地図の市区町村をタップしても、一覧の行を押しても、同じ市区町村詳細へ移動します。

**市区町村の色**は5段階です。

| 段階 | 意味 |
| --- | --- |
| 0 | 未訪問 |
| 1〜4 | 訪問済み（訪問回数が多いほど濃く） |

濃さの求め方は `shadeLevel(entry, metric)` に切り出してあり、
`metric` を `"favorites"` に変えるとお気に入り数による濃淡になります。
`area_stats()` がすでにお気に入り数を返しているため、色の基準を足すだけで切り替えられます。

### 3-3. 市区町村の境界データ

- 出典: [smartnews-smri/japan-topography](https://github.com/smartnews-smri/japan-topography)（簡素化1%）
- `scripts/build-municipality-paths.mjs` で SVG パスへ変換
- 出力: `src/lib/geo/municipality-paths/{都道府県コード}.json`（全国で約2MB、1県あたり8〜139KB）
- **サーバー側で開いている県の分だけ読み込む**ため、端末に届くのは
  その県の SVG パスだけです（都道府県画面の First Load JS は 110KB のまま）

**離島の扱い**も都道府県スケール用に作り直しました。東京都のように本土が小さく
離島が広がる県では、そのまま描くと本土がつぶれてしまいます。

| 都道府県 | 枠に寄せる島 |
| --- | --- |
| 東京都 | 伊豆諸島・小笠原諸島 |
| 鹿児島県 | 奄美群島 |
| 沖縄県 | 先島諸島・大東諸島 |

枠の位置と縮尺は、本体の大きさから自動で決めています（手作業の調整は不要）。
日本地図・地方地図での見え方はこれまでどおりです。

## 4. 追加テーブル・カラム / RLS

### 追加したテーブル

**ありません。**

### 変更した関数

`supabase/migrations/0003_workspace_area_stats.sql`

| 関数 | 変更 |
| --- | --- |
| `area_stats(p_trip_ids uuid[] default null)` | 旅行での絞り込みを追加。`favorite_count` を戻り値に追加 |

```sql
select s.prefecture_code, s.municipality_code,
       count(distinct s.id)                  as spot_count,
       count(vr.id)                          as visit_count,
       count(*) filter (where vr.favorite)   as favorite_count,
       max(vr.visited_at)                    as last_visited_at
from public.visit_records vr
join public.spots s on s.id = vr.spot_id
where p_trip_ids is null or vr.trip_id = any (p_trip_ids)
group by s.prefecture_code, s.municipality_code;
```

### RLS の変更

**ありません。** 詳しくは「2. 影響範囲 › RLS」を参照してください。

RLS テストに、ワークスペース分離の確認を4件追加しました（合計91件・すべて成功）。

- 一人旅だけを指定すると、その市区町村だけが集計される
- 共有旅だけを指定すると、その市区町村だけが集計される
- 一人旅と共有旅で市区町村が混ざらない
- 参加していない旅行 ID を渡しても、RLS により何も集計されない

## 5. 未対応の項目

### ワークスペースの記憶方法

開いている旅は Cookie に保存しています。URL には現れないため、
**同じアカウントで2つのタブを開くと、あとから切り替えたほうに揃います。**
URL に含める方式（`/w/{id}/home` など）にすれば解消できますが、
全画面のパス変更が必要になるため、「最小限の変更で」というご要望を優先しました。

### 市区町村地図の拡大・移動

拡大や移動はできません。東京23区や大阪市の区のように小さな市区町村は、
地図上では小さく表示されます（押しやすいように、小さいものには丸い目印と
広めの当たり判定を重ねています）。実際の選択は下の一覧・検索が確実です。

### 小笠原諸島などの極端に小さい島

枠の中に実際の大きさで描いているため、点ほどの大きさになります。
枠と見出しで存在は分かりますが、地図から選ぶのは難しいため一覧をお使いください。

### お気に入り数による濃淡

段階の求め方（`shadeLevel`）と集計（`favorite_count`）は用意しましたが、
画面から基準を切り替える導線は付けていません。

### スポットの重複

同じスポットを複数のワークスペースで訪問した場合、`spots` の行は共有され、
訪問履歴だけがワークスペースごとに分かれます。スポット詳細の訪問履歴は
いまのワークスペースの分だけを表示します。

### 実 Supabase プロジェクトでの確認

前回と同じく、接続先がないため未実施です。
`./scripts/verify-rls.sh`（91項目・成功）と `node scripts/verify-supabase.mjs` をご利用ください。

## 6. 今後の改善案

1. **ワークスペースを URL に含める**（`/w/{id}/…`）。
   タブごとに別の旅を開けるようになり、リンクの共有もできます。
2. **市区町村地図の拡大・移動**。都市部の区が選びやすくなり、
   地図から場所を選ぶときの精度も上がります。
3. **色の基準を画面から切り替える**。訪問回数・お気に入り数・最終訪問日など。
4. **ワークスペースごとの通知**。共有旅に動きがあったとき、
   その旅を開いていなくても分かるようにする。
5. **境界データの更新手順**。市区町村の合併に備えて、
   `scripts/build-municipality-paths.mjs` の入力を定期的に更新する運用を決める。
6. **一人旅を複数のワークスペースに分ける**。
   いまは一人旅をすべて「自分の旅」にまとめていますが、
   「日常」「登山」のように分けたい場合は、ワークスペースの定義を
   `trips` のグループへ広げることになります。
