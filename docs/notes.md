# 実装メモ・仕様の補足

仕様書（版数 1.0）に対する実装上の判断と、現時点の制限事項をまとめています。

## 仕様書からの補足・変更点

### テーブル定義に追加した列

`visit_records` に、仕様書の入力項目を保存するための列を追加しています。

| 列 | 対応する入力項目 | 追加理由 |
| --- | --- | --- |
| `companions` | 一緒に行った人 | 仕様書16章の入力項目にあるが、20章のテーブル定義に列がなかったため |
| `note` | メモ | 「感想」を `comment`、「メモ」を `note` として分けて保存するため |

### `profiles` の主キー

仕様書では `id` と `user_id` の両方が挙げられているため、`id` を独立した主キー、
`user_id` を `auth.users` への一意な外部キーとしています。アプリ側の検索は `user_id` で行います。

### スポットの評価・お気に入り・訪問回数

`spots` テーブルには評価やお気に入りの列を持たせず、紐づく `visit_records` から集計しています。

- 評価 = 訪問履歴の評価の平均
- お気に入り = いずれかの訪問履歴でお気に入りが付いている
- 訪問回数・最終訪問日 = 訪問履歴の件数と最新日

同じスポットへの再訪問はスポットを重複登録せず、訪問履歴を追加する形になります（仕様書15章）。

### スポットの代表写真

`spots` に写真用の列はないため、最後に訪れた訪問履歴の1枚目を代表写真として表示しています。

### 緯度・経度

座標の決め方は `spots.location_source` に保存します。市区町村を選んだだけなら
その市区町村の代表座標（`municipality`）、現在地や地図選択を使えばその座標（`device` / `map`）です。
番地単位の測位は行いません。詳しくは [`changes-2.md`](changes-2.md) の④を参照してください。

## 制限事項

### 共有旅は廃止しました（第4版）

複数人で記録を共有する「共有旅」は取りやめ、自分ひとりで記録するアプリにしました。
招待・メンバー・コメント・活動履歴とメール送信の仕組みは、画面・コード・データベースの
すべてから削除しています（`supabase/migrations/0008_remove_shared_trips.sql`）。

移行時の扱いは次のとおりです。

| 対象 | どうなるか |
| --- | --- |
| 共有旅として作った旅行 | 持ち主の個人の旅行として残る（記録・写真もそのまま） |
| 他の人の共有旅に自分が書いた記録 | 書いた本人の旅行へ移す。移さないと誰からも見えなくなるため |
| 招待・メンバー・コメント・活動履歴 | 削除（元に戻せない） |

### 市区町村の地図表示

都道府県詳細は、上に市区町村の境界地図、下に検索と一覧を並べたハイブリッド構成です。
地図をタップしても一覧を押しても、同じ市区町村詳細へ移動します。
拡大・移動はできないため、小さな市区町村は一覧から選ぶほうが確実です。

### 沖縄県・離島

本土から離れた島は、破線の枠に入れて余白へ寄せて描いています
（そのままの位置だと地図が横に広がり、本土が小さくなるため）。
寄せる島は縮尺ごとに変えています。

| 縮尺 | 枠に寄せる島 |
| --- | --- |
| 日本地図・地方地図 | 沖縄本島・先島諸島・大東諸島・小笠原諸島 |
| 都道府県地図 | 上記に加えて、伊豆諸島（東京都）・奄美群島（鹿児島県） |

南鳥島・沖ノ鳥島は離れすぎるため描いていません（小笠原村として一覧・記録では扱えます）。

### 写真の孤立ファイル

保存前の写真は一時領域 `tmp/{user_id}/{下書きID}/` へ置き、保存時に本来の場所へ移します。
`tmp/` を許可する Storage ポリシー（`0002` / `0007`）が当たっていないデータベースでは書き込めないため、
その場合は予備の一時領域 `users/{user_id}/uploads/{下書きID}/` へ自動で切り替えます。
`users/{user_id}/` は最初のマイグレーションから自分専用の領域として許可されているので、
ポリシーの適用状況にかかわらずアップロードできます。扱い（保存時の移動・片づけ）は `tmp/` と同じです。
保存せずに離れたファイルは一時領域に残り、12時間を過ぎたものをアプリ起動時（1日1回）に削除します。
しばらくアプリを開かない利用者のファイルは残るため、サーバー側での定期実行は今後の課題です。

### 訪問回数による色分け

塗り分けは縮尺で異なります。

| 地図 | 塗り分け |
| --- | --- |
| 日本地図・地方地図（`AreaMap`） | 未訪問 / 訪問済みの2段階 |
| 都道府県地図・エリア地図（`MunicipalityMap`） | 訪問回数に応じた5段階 |

段階は `shadeLevel()` が 0〜4 で返し、`MunicipalityMap` の `FILL` / `STROKE`
（5色）がそのまま対応しています。`AreaMap` は訪問の有無だけを見ているため、
こちらも段階を増やす場合は色指定を足すことになります。

## 自分の旅の名前

ホームと記録画面の上に出る名前は `profiles.space_name` に保存します。
未設定なら「自分の旅」（`DEFAULT_SPACE_NAME`）を使い、マイページの
「プロフィールを編集」から変更できます。空にすると既定へ戻ります。

旅ワークスペース（開いている旅を Cookie に保存して切り替える仕組み）は、
共有旅の廃止にあわせて削除しました。記録の置き場所はひとつだけです。

## 動作確認について

Supabase プロジェクトに接続した状態での実行確認は行っていません
（この作業環境から接続できる Supabase プロジェクトがないため）。

代わりに、次の2つを用意しています。

```bash
./scripts/verify-rls.sh          # ローカル PostgreSQL で RLS・RPC を検証（73項目）
node scripts/verify-supabase.mjs # 実 Supabase プロジェクトでの動作確認
```

型チェック・ESLint・本番ビルドは通っています。
詳細は [`changes-4.md`](changes-4.md) と [`changes-3.md`](changes-3.md) を参照してください。
