# アプリ「インフラ」設計メモ

アプリの画面（ホームを左にスワイプした画面）に置く、Web のインフラ（サーバーのしくみ）を
**目で見て・さわって**学べるアプリ。ルート: `/infra`、コード: `src/components/infra/`。

## 1. ねらい

- 「サーバー」「DNS」「ロードバランサー」「キャッシュ」…といった言葉を、**動く図**で直感的に分かるようにする
- 読むだけの教材にしない。**自分で組み立てて、本番を動かして、こわれるのを見て、直す**ことで覚える
- 1ステージ数分。毎回ちがう問題（アクセス急増・故障・攻撃）が起きるので、くり返し遊んでも飽きない

## 2. コンセプト：「わんこ商店のサーバー係」

わんこが始めたネットのお店（サービス）が、だんだん人気になっていく。
利用者が増えるたびに新しい問題が起きるので、プレイヤーはサーバー係として設備（パーツ）を足して乗りこえる。
ステージを進めると、**小さなサーバー1台から、本物の大きなサービスと同じ構成**まで育っていく。

## 3. 遊びの流れ（1ステージ）

1. **せつめい**：せんせい（フレンチー）が、今回の問題としくみを動く図とたとえ話で説明（2〜3枚）
2. **くみたて**：空いているマスをタップして、パーツを置く（予算あり）。線は自動でつながる
3. **ほんばん**：利用者のアクセス（光る点）が流れはじめる。点がサーバーへ行き、返事が戻ってくる
   - 混むとサーバーが赤く光ってゆれ、あふれた分は「503」で断られる
   - 途中で「アクセス急増」「サーバー故障」「攻撃」などの事件が起きる
   - 本番中もパーツを足せる（障害対応ごっこ。あとから足すと月額の平均が安くすむ＝従量課金の体験）
4. **けっか**：★（成功率・速さ・コスト）、時間ごとのグラフ、学んだことのまとめ
5. **ふりかえりクイズ**（1問）→ 正解で「理解」バッジ。用語カードが図鑑に入る

## 4. 飽きさせない工夫

- 光る点・線の流れ・混雑の赤い光・故障の煙・HIT の文字など、**状態がひと目で分かる演出**
- 利用者の顔（にこにこ → こまり顔）で、サービスの良し悪しが伝わる
- ★3つ目は「コスト」。ギリギリの構成や、混んでから増やす運用を考える余地を残す
- 本番中に事件が起き、その場でパーツを足して立て直せる
- 図鑑（用語カード）集め、クイズのバッジ
- クリア後は「ラボ」で、アクセス数・攻撃・故障を自由に起こして実験できる
- 最後に「このアプリの裏側」：いま使っているこのアプリ自体の構成（Vercel・Supabase）を、学んだパーツで見せる

### ステージを追加・調整するとき

1. `stages.ts` に `StageDef` を足す（説明カード・マス・はじめから置くもの・予算・目標・交通量・事件・ヒント・まとめ・クイズ・用語・お手本）
2. 新しい用語は `glossary.ts` に足す（ステージの `terms` と id をそろえる）
3. `node scripts/simulate-infra.mjs 40 <ステージid>` で、「そのまま」が★0、「お手本」が★3 になることを確かめる。
   別のやり方（力ずく・まちがった直し方）は、スクリプトの `ALTERNATIVES` に足して、★が欠けることを確かめる
4. この表を更新する

## 6. 画面

- **トップ**：タブ「ステージ」「ずかん」「ラボ」。ステージは路線図のように縦に並ぶ（★・理解バッジつき）
- **ステージ**：上に成績（成功率・平均の速さ・月額）と時間のバー、まんなかに盤面、その下にフレブル先生のひとこと欄（ヒント）、いちばん下に操作。
  盤面には何も重ねない（事件のお知らせだけ、盤面の下の空きに短く出す）
- **盤面**（縦長・スマホ向け）：上から 利用者 → 入口（DNS・CDN・WAF）→ ロードバランサー → サーバー → データ（キャッシュ・DB・キュー）→ ワーカー
  - 線・光る点・効果は canvas、パーツのタイルは DOM（タップしやすく、文字がくっきり）
- **パーツをタップ**：役割・たとえ・いまの数字（処理中・待ち・ヒット率）・サイズ変更（スケールアップ）・取り外し

## 7. シミュレーションのルール（`sim.ts`）

画面の動きは本物の約100倍ゆっくり。表示する「ms」は、ゲーム内の1秒＝100ms として換算したイメージの数字。

- アクセスの種類：ページ（水色）・画像（黄）・投稿（ピンク）・重い処理（紫）・攻撃（赤）。返事はミント色、DNS への問い合わせは白い輪、裏の仕事はオレンジの四角
- 各パーツは「同時に処理できる数」と「1件の処理時間」を持つ。いっぱいなら待ち行列、待ち行列もいっぱいなら「503」で断る
- 時間がかかりすぎたアクセスはタイムアウト（504）
- ロードバランサーは、すいているサーバーへ振り分ける。止まったサーバーには、ヘルスチェックで気づいてから送らなくなる
- ロードバランサーがないと、DNS が指す1台にしかアクセスが来ない（サーバーを増やしても使われない）
- データベースがないと、投稿はそれを受けたサーバーにだけ残る（別のサーバーで読むと「見つからない」）
- キャッシュ・CDN は、使われるほど中身がたまってヒット率が上がる
- 予備DB は読みこみを分担し、本番DB が止まると本番に昇格する（フェイルオーバー）
- キューがあると、重い処理は受付だけしてすぐ返事をし、ワーカーが裏で処理する。キューで8秒より長く待った仕事は「期限切れ」（失敗）。
  加工の完成も成功に数える（ワーカーが足りないと成功率が下がる）
- WAF は攻撃の大部分を入口で止める
- 月額は「置いていた時間」で平均する（従量課金）

成績：

- 成功率 = 返事ができたアクセス ÷ 攻撃以外の全アクセス
- ★1：成功率が目標以上（クリア） / ★2：平均の速さが目標以内 / ★3：月額（平均）が目標以内

## 8. ファイル構成

- `src/app/(app)/infra/page.tsx` … ページ（`loading.tsx` は暗い待ち画面）
- `src/components/infra/`
  - `model.ts` … パーツ・アクセスの種類・数値
  - `stages.ts` … ステージ（交通量・事件・目標・説明・クイズ）
  - `glossary.ts` … 用語カード
  - `sim.ts` … シミュレーター（React に依存しない。乱数は種つきで、同じ条件なら同じ結果）
  - `layout.ts` … 盤面のマスの位置と線
  - `render.ts` … canvas の描画
  - `board.tsx` / `stage-play.tsx` / `infra-app.tsx` / `lab.tsx` … 画面
- `scripts/simulate-infra.mjs` … 各ステージを「お手本の構成」と「何もしない構成」で何度も動かして、
  目標値がちょうどよいか確かめる（`node scripts/simulate-infra.mjs`）
- アイコン：`public/launcher/icons/infra.webp`
