# アプリ「インフラ」設計メモ

アプリの画面（ホームを左にスワイプした画面）に置く、Web のインフラ（サーバーのしくみ）を
**目で見て・さわって**学べるアプリ。ルート: `/infra`、コード: `src/components/infra/`。

## 1. ねらい

- 「サーバー」「DNS」「ロードバランサー」「キャッシュ」…といった言葉を、**動く図**で直感的に分かるようにする
- 読むだけの教材にしない。**自分で組み立てて、本番を動かして、こわれるのを見て、直す**ことで覚える
- 1ステージ数分。毎回ちがう問題（アクセス急増・故障・攻撃）が起きるので、くり返し遊んでも飽きない

## 2. コンセプト：「わんこ商店のサーバー係」

わんこが始めたネットのお店（サービス）が、だんだん人気になっていく。
利用者が増えるたびに新しい問題が起きるので、プレイヤーはサーバー係として設備（パーツ）を足して乗りこえる。
ステージを進めると、**小さなサーバー1台から、本物の大きなサービスと同じ構成**まで育っていく。

## 3. 遊びの流れ（1ステージ）

1. **せつめい**：せんせい（フレンチー）が、今回の問題としくみを動く図とたとえ話で説明（2〜3枚）
2. **くみたて**：空いているマスをタップして、パーツを置く（予算あり）。線は自動でつながる
3. **ほんばん**：利用者のアクセス（光る点）が流れはじめる。点がサーバーへ行き、返事が戻ってくる
   - 混むとサーバーが赤く光ってゆれ、あふれた分は「503」で断られる
   - 途中で「アクセス急増」「サーバー故障」「攻撃」などの事件が起きる
   - 本番中もパーツを足せる（障害対応ごっこ。あとから足すと月額の平均が安くすむ＝従量課金の体験）
4. **けっか**：★（成功率・速さ・コスト）、時間ごとのグラフ、学んだことのまとめ
5. **ふりかえりクイズ**（1問）→ 正解で「理解」バッジ。用語カードが図鑑に入る

## 4. 飽きさせない工夫

- 光る点・線の流れ・混雑の赤い光・故障の煙・HIT の文字など、**状態がひと目で分かる演出**
- 利用者の顔（にこにこ → こまり顔）で、サービスの良し悪しが伝わる
- ★3つ目は「コスト」。ギリギリの構成や、混んでから増やす運用を考える余地を残す
- 本番中に事件が起き、その場でパーツを足して立て直せる
- 図鑑（用語カード）集め、クイズのバッジ
- 「ラボ」は自由設計の実験室。パーツを好きな数だけ置き、線を自由につないで、アクセス数・攻撃・故障を起こして実験できる。
  組み立てた構成は、本物の設定ファイル（docker-compose・Terraform）にして見られる（下の「ラボ（自由設計）」）
- 最後に「このアプリの裏側」：いま使っているこのアプリ自体の構成（Vercel・Supabase）を、学んだパーツで見せる

## 6. 画面

- **トップ**：タブ「ステージ」「ずかん」「ラボ」「サーバー室」。ステージは路線図のように縦に並ぶ（★・理解バッジつき）
- **ステージ**：上に成績（成功率・平均の速さ・月額）と時間のバー、まんなかに盤面、その下にフレブル先生のひとこと欄（ヒント）、いちばん下に操作。
  盤面には何も重ねない（事件のお知らせだけ、盤面の下の空きに短く出す）
- **盤面**（縦長・スマホ向け）：上から 利用者 → 入口（DNS・CDN・WAF・右はしに予備の拠点）→ ロードバランサー（右にオートスケール）
  → サーバー → データ（キャッシュ・DB・予備DB・キュー・バックアップ）→ 裏方（ワーカー・左はしに監視）
  - 線・光る点・効果は canvas、パーツのタイルは DOM（タップしやすく、文字がくっきり）
- **パーツをタップ**：役割・たとえ・いまの数字（処理中・待ち・ヒット率）・サイズ変更（スケールアップ）・取り外し

## 6.5 ラボ（自由設計）

- マスの決まりはない。「＋ パーツ」で、使えるパーツ（クリアしたステージで習ったもの）を種類ごとの上限まで置ける
  （サーバー6・ワーカー4・予備DB 2・ほかは1。`design.ts` の `LIMITS`）
- 置くと、ふつうのつなぎ方のうちそのパーツにかかわる線だけ自動で足す。CDN・WAF・ロードバランサーを置いた・外したときは、
  入口の並びが変わるので全体を組みなおす。「自動でつなぐ」で、いつでもふつうのつなぎ方にもどせる
- 「線をつなぐ」：2つを順にタップすると、つなぐ（つながっていたら外す）。いちばん上の利用者の列もタップできる。
  つないでよい組み合わせは `layout.ts` の `CAN_LINK`（例：サーバー → キャッシュ・DB・予備DB・キュー、キュー → ワーカー）
- シミュレーターは、線のとおりにアクセスを流す。利用者から入口が2つあれば順番に振り分ける（DNS ラウンドロビン）。
  届かないパーツ・見張る相手のない監視などは、盤面の下に注意を出す
- 設計図はこの端末に覚えておく（localStorage `odekake_infra_lab_v2`）
- 「本物の設定にする」：`export.ts` が、docker-compose.yml・nginx.conf（ロードバランサーがあるとき）・main.tf（AWS の Terraform）を作る。
  線のつなぎ方（ロードバランサーの振り分け先、サーバーがつながる DB・キャッシュ・キュー など）も反映する。
  本物の値が要るところ（AMI・ネットワーク・パスワード）は variable。予備DB のレプリケーションの本番側の設定は省略（ファイルにも書いてある）
- 確かめかた（2026-10-08）：いろいろな構成（全部入り・最小・LB なし・WAF → サーバー直結・オートスケール・CDN → サーバー・停電対策・キューだけ）で、
  docker-compose.yml は `docker compose config`、main.tf は `terraform fmt -check` と `terraform validate`（AWS プロバイダ 5.70）がすべて通ることを確かめた

## 6.6 サーバー室（本物のプログラムで動くサーバー）

タブ「サーバー室」。シミュレーションではなく、本物のプログラムと本物の HTTP でやりとりする（`room.ts`・`server-room.tsx`・`room-templates.ts`）。

- サーバー … 1〜3台の Web Worker。自分で書いた `onRequest(request, env)` が、本物の `Request` を受けて `Response` を返す
  （Cloudflare Workers などと同じ形）。「デプロイ」で、全部のサーバーを新しいプログラムで作りなおす
- 外とつながる道具（fetch・XMLHttpRequest・WebSocket・indexedDB など）は Worker の中で消してあるので、
  サーバーのプログラムはブラウザの外へ何も送れない。固まったら（無限ループなど）terminate して作りなおす
- ロードバランサー … 1.5秒ごとに `GET /health` を送り（ヘルスチェック）、2xx を返したサーバーにだけ振り分ける（順番に／すいている方）。
  3秒たっても返事がなければ 504、止まっていれば 502、元気なサーバーが0台なら 503
- 監視（オン／オフ）… ヘルスチェックに2回続けて失敗したサーバーを、自動で再起動する
- CDN（オン／オフ）… 返事の `Cache-Control: max-age` を読んで、その秒数だけ同じ返事を使い回す（`X-Cache: HIT／MISS`・`Age`）
- データベース `env.db`（get・put・delete・list・incr。この端末に保存、300件まで）とキャッシュ `env.cache`（get・put（秒数））は、
  この画面が持っていて、どのサーバーからも同じ中身が見える
- ヘッダーの値は英数字だけ（本物の HTTP と同じ。日本語を入れると Request・Response が作れない）
- お手本：はじめてのサーバー・データベースを使う・キャッシュで速く・CDN に覚えてもらう・こわれやすいサーバー（エラー・遅い・固まる）
- 確かめかた（2026-10-08、Chromium）：ヘルスチェックの合格、20回まとめて送ると2台に10件ずつ、DB の書きこみと読みこみ、
  CDN の2回目が HIT、/freeze で 504 → ヘルスチェックで外れる → 監視オンで自動再起動、文法エラーの表示と 503、
  Worker の中から fetch・XMLHttpRequest・indexedDB が使えないこと

## 7. シミュレーションのルール（`sim.ts`）

- アクセスは「リンク」（a → b のつながり）のとおりに流れる。ステージでは置いたパーツからふつうのつなぎ方が決まり（`layout.ts` の `computeLinks`）、
  ラボでは自分でつないだリンクを使う。リンクのしくみに変えたとき、ステージ1〜14 の検証結果が1件も変わらないことを確かめた

画面の動きは本物の約100倍ゆっくり。表示する「ms」は、ゲーム内の1秒＝100ms として換算したイメージの数字。

- アクセスの種類：ページ（水色）・画像（黄）・投稿（ピンク）・重い処理（紫）・攻撃（赤）。返事はミント色、DNS への問い合わせは白い輪、裏の仕事はオレンジの四角
- 各パーツは「同時に処理できる数」と「1件の処理時間」を持つ。いっぱいなら待ち行列、待ち行列もいっぱいなら「503」で断る
- 時間がかかりすぎたアクセスはタイムアウト（504）
- ロードバランサーは、すいているサーバーへ振り分ける。止まったサーバーには、ヘルスチェックで気づいてから送らなくなる
- ロードバランサーがないと、DNS が指す1台にしかアクセスが来ない（サーバーを増やしても使われない）
- データベースがないと、投稿はそれを受けたサーバーにだけ残る（別のサーバーで読むと「見つからない」）
- キャッシュ・CDN は、使われるほど中身がたまってヒット率が上がる
- 予備DB は読みこみを分担し、本番DB が止まると本番に昇格する（フェイルオーバー）
- キューがあると、重い処理は受付だけしてすぐ返事をし、ワーカーが裏で処理する。キューで8秒より長く待った仕事は「期限切れ」（失敗）。
  加工の完成も成功に数える（ワーカーが足りないと成功率が下がる）
- WAF は攻撃の大部分を入口で止める
- 月額は「置いていた時間」で平均する（従量課金）
- オートスケール：サーバーの混み具合（処理中＋待ち ÷ 同時に処理できる数）を見て、0.6 をこえたら休んでいるサーバーを
  1台起こし（起きるまで2秒）、0.3 を下回ったら1台休ませる（手もちを片づけてから）。休んでいるサーバーは月額 0 円。
  オートスケールがあると、本番の始めはいちばん前のサーバーだけが起きている。置いたサーバーの数が増やせる上限
- 監視：止まったサーバー・DB や、遅くなったサーバー（処理が7倍遅い。ヘルスチェックでは気づけない）に1秒で気づき、
  2秒で再起動する。ないと、事件の長さのあいだずっと直らない。停電は直せない
- バックアップ：4秒ごとに本番DB を保存する。DB の中身が消えると（予備DB にも写る）、1.2秒で気づいて2.5秒で元にもどす。
  消える前に保存したものがないと、もどせない。消えているあいだのページの読みこみは「データ消失」で失敗
- 停電：DNS・CDN・予備の拠点・監視・バックアップ以外が、まるごと止まる。DNS は1秒で気づいて、それからの問い合わせには
  予備の拠点（大阪）を教える。利用者は DNS の答えを TTL（ふつう15秒・短め3秒）のあいだ覚えていて、そのあいだは止まった拠点へ行く。
  予備の拠点はサーバーと DB がひとまとめで、少し遠い

成績：

- 成功率 = 返事ができたアクセス ÷ 攻撃以外の全アクセス
- ★1：成功率が目標以上（クリア） / ★2：平均の速さが目標以内 / ★3：月額（平均）が目標以内
