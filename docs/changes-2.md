## 1. 修正内容一覧

### ① Supabase 実環境での確認

**この作業環境から接続できる Supabase プロジェクトがないため、実環境での実行確認はできていません。**
代わりに、確認を2通りの形で自動化しました。

| やったこと | ファイル | 状態 |
| --- | --- | --- |
| ローカル PostgreSQL 上で RLS・RPC・トリガーを検証（87項目） | `supabase/tests/`, `scripts/verify-rls.sh` | **87件すべて成功** |
| 実 Supabase プロジェクト向けの動作確認スクリプト | `scripts/verify-supabase.mjs` | 未実行（要・接続先） |

ローカル検証は、素の PostgreSQL に Supabase 相当の土台（`auth.users` / `auth.uid()` /
`storage.objects` / `storage.foldername()` など）を作り、`supabase/migrations/*.sql` を
そのまま適用して行います。ご依頼の確認項目に対応するテストが含まれています。

```bash
./scripts/verify-rls.sh          # ローカル検証（Supabase への接続は不要）
node scripts/verify-supabase.mjs # 実プロジェクトでの確認
```

この検証で、**実環境なら必ず失敗していた不具合が2件見つかり、修正しました。**

1. **招待コードでの参加が必ず失敗していた**
   `join_trip_by_code()` の戻り値の列名 `trip_id` と、関数内の
   `on conflict (trip_id, user_id)` の列参照がぶつかり、実行時に
   `column reference "trip_id" is ambiguous` で失敗していました。
   重複チェックを `on conflict` から例外処理に変えて解消しています。
2. **共有旅の表紙画像がアップロードできなかった**
   新規作成時に `trips/{trip_id}/cover/` へ直接アップロードしていましたが、
   保存先の権限判定 `can_access_trip()` は旅行が既に存在することを前提にしており、
   作成前は必ず拒否されていました。⑤の一時領域の導入で解消しています。

`scripts/verify-supabase.mjs` は、新規登録 → 確認メールの設定 → ログイン →
一人旅の非公開 → 共有旅の未参加ユーザー拒否 → 写真のアップロードと署名付き URL →
アカウント削除、までを実際のプロジェクトに対して順に確認します。
テスト用アカウントの作成と後片づけまで行うので、そのまま実行できます。

### ② メールアドレスによる招待

### ④ スポットの位置

  現在地は端末の測位精度をそのまま誤差として保存します。
- どうやって決めた座標かを `spots.location_source` に保存するため、
  あとから精度の高い座標へ置き換えても由来が分かります。
- 店舗検索は `src/lib/places/` の `PlaceSearchProvider` を実装して

### ⑤ 写真の孤立ファイル対策

保存前の写真は一時領域へ置き、保存時に本来の場所へ移す方式にしました。

```
tmp/{user_id}/{下書きID}/...        ← アップロード直後（未保存）
    ↓ 保存時に移動
trips/{trip_id}/visits/{visit_id}/...
trips/{trip_id}/cover/...
users/{user_id}/profile/...
```

- 保存せずに離れた写真は一時領域に残るだけで、本来の場所を汚しません。
- 一時領域のファイルは12時間で期限切れとし、アプリを開いたとき1日1回まとめて削除します。
- 保存済みの写真を画面から外したときは、フォームを保存するまで実ファイルを消さないようにしました
  （保存せずに離れると写真だけが消えてしまう問題があったため）。
- アカウント削除時に、自分の旅行・プロフィール・一時領域のファイルをまとめて削除します。

## 2. 修正理由

| 項目 | 理由 |
| --- | --- |
| ローカル RLS 検証を用意した | 実プロジェクトに接続できないため。実際に不具合が2件見つかり、想定どおり役に立った |
| 招待にメール送信の状態を持たせた | 「送っていない招待」と「送った招待」を区別できないと、後から送信を足したときに二重送信になるため |
| 市区町村を点で描いた | 全国1,894件の境界データは容量が大きすぎるため、代表座標での配置図にした |
| 座標の由来を保存する | 代表地点と実測値が混ざると、地図の精度をどこまで信用してよいか分からなくなるため |
| 代表座標を作り直した | 69件が県外を指しており、地図表示とスポット登録の両方で実害が出るため |
| 一時領域を経由する | 保存前の写真が本来の場所に残ると、どれが未使用か判別できないため |
| 活動履歴をトリガーで記録する | アプリ側の書き忘れがなくなり、どの経路の更新でも確実に残るため |
| 活動履歴の対象名を写しておく | 参照先が消えたときに「何を」が読めなくなるため |
| 離島を枠で描いた | そのまま描くと地図が横に広がり本土が小さくなるが、省くと訪問記録が地図に出ないため |

## 3. 追加したテーブル・カラム

すべて `supabase/migrations/0002_invitations_location_activities.sql` です。
0001 を適用済みのプロジェクトにそのまま追加できます（何度実行しても同じ結果になります）。

### 追加したテーブル

**`trip_activities`** — 共有旅の活動履歴

| 列 | 型 | 説明 |
| --- | --- | --- |
| `id` | uuid | 主キー |
| `trip_id` | uuid | 対象の旅行（削除時は連鎖） |
| `actor_id` | uuid | 実行者（退会時は null） |
| `action` | trip_activity_action | 操作の種類 |
| `target_type` | text | `trip` / `member` / `visit` / `photo` / `comment` |
| `target_id` | uuid | 対象の ID |
| `target_label` | text | 対象の名前（保存時に写す） |
| `detail` | jsonb | 補足（写真の枚数など） |
| `created_at` | timestamptz | 記録した日時 |

### 追加した列

**`trip_invitations`**

| 列 | 型 | 説明 |
| --- | --- | --- |
| `invited_by` | uuid | 招待した人 |
| `message` | text | 招待に添えるひとこと |
| `email_status` | text | `not_sent` / `queued` / `sent` / `failed` |
| `email_sent_at` | timestamptz | 送信できた日時 |
| `email_error` | text | 送信に失敗した理由 |
| `email_attempts` | smallint | 送信を試みた回数 |
| `accepted_by` | uuid | 参加した人 |
| `accepted_at` | timestamptz | 参加した日時 |

**`spots`**

| 列 | 型 | 説明 |
| --- | --- | --- |
| `location_source` | location_source | `municipality` / `address` / `map` / `device` / `place_search` |
| `location_accuracy_m` | double precision | 位置の誤差の目安（メートル） |
| `location_updated_at` | timestamptz | 位置を決めた日時 |
| `place_provider` | text | 店舗検索の提供元 |
| `place_id` | text | 提供元での施設 ID |
| `postal_code` | text | 郵便番号 |
| `phone` | text | 電話番号 |

### 追加した型・制約・索引

- 列挙型 `location_source`、`trip_activity_action`
- `trip_invitations` — メール形式の検査、`email_status` の値の検査、
  同じ宛先の招待中が重複しない一意索引、送信待ちを取り出す索引
- `spots` — 緯度経度の範囲の検査、誤差が負でない検査、`(created_by, place_provider, place_id)` の一意索引
- `trip_activities` — `(trip_id, created_at desc)` の索引

### 変更した関数

| 関数 | 変更 |
| --- | --- |
| `join_trip_by_code()` | 列名の衝突を解消（**実行時エラーの修正**）。参加者と参加日時を記録 |
| `delete_own_account()` | 削除できたことを確認し、できていなければ例外にする |
| `can_access_storage_path()` | 一時領域 `tmp/{user_id}/...` を許可 |
| `is_shared_trip()` / `log_trip_activity()` | 新規。活動履歴の記録に使う |
| `tg_*_activity()` | 新規。旅行・メンバー・訪問記録・写真・コメントのトリガー |

## 4. RLS の変更内容

**既存のポリシーの公開範囲は変えていません。** 追加・変更は次のとおりです。

### 追加

```sql
-- trip_activities: 閲覧はその旅行を見られる人だけ
create policy trip_activities_select on public.trip_activities for select to authenticated
  using (public.can_access_trip(trip_id));
```

書き込みのポリシーは**あえて作っていません**。履歴の追加は security definer の
トリガー経由だけになり、クライアントから履歴を捏造できません
（テストで拒否されることを確認しています）。

### 変更

Storage の `photos` バケットの権限判定 `can_access_storage_path()` に、一時領域を追加しました。

```sql
if parts[1] = 'tmp' or parts[1] = 'users' then
  return parts[2] = auth.uid()::text;   -- 自分のフォルダだけ
elsif parts[1] = 'trips' then
  return public.can_access_trip(v_id);  -- 従来どおり
end if;
```

`tmp/` は自分の分しか読み書きできません（他人の一時領域への書き込みが
拒否されることをテストで確認しています）。ポリシー本体（`photos_select` など）は変更していません。

### 検証した公開範囲

`supabase/tests/01_rls.test.sql` の87項目のうち、ご指摘の観点は次のとおりです。

- 一人旅 — 本人以外（共有旅の仲間・第三者）から旅行・記録・スポットが見えない
- 共有旅 — 未参加ユーザーから旅行・記録・スポット・メンバー・コメント・活動履歴が見えず、書き込みもできない
- 写真 — 他人の一時領域に書けない、未参加ユーザーが共有旅の写真を置けない・読めない
- 編集権限 — メンバーは自分の記録だけ、オーナーは旅行内すべて
- 退出・除外 — オーナーは外せない、メンバーは自分で退出できる
- アカウント削除 — 自分のデータだけが消え、他ユーザーの旅行と記録は残る

## 6. 今後の改善案

### すぐに効果が出るもの

1. **招待メールの送信を足す**（`Mailer` を1つ実装するだけ）。
   `email_status` を見て未送信の招待をまとめて送る処理も書けます。
2. **一時領域の掃除をサーバー側でも回す**。
   いまはアプリを開いたときに1日1回です。しばらくアプリを開かない利用者のファイルは残るため、
   Edge Function + pg_cron で定期実行すると確実になります。
3. **店舗検索の提供元を1つ追加する**。`PlaceSearchProvider` を実装すれば、
   スポット名・住所・座標がまとめて入力できるようになります。

### データの持ち方

4. **アカウント削除の連鎖を見直す**。
   いまは `spots.created_by` が連鎖削除のため、共有旅でスポットを登録した人が退会すると、
   **他のメンバーの訪問記録も一緒に消えます**。スポットを残す（`created_by` を null 許容にする）か、
   旅行に紐づくスポットは旅行の所有にする、といった変更が考えられます。
5. **市区町村の境界データを持つ**。いまは代表座標の配置図です。
   簡略化した境界（全国で 1〜2MB 程度）を用意すれば、市区町村単位の塗り分けができます。
6. **`visit_photos` に幅・高さ・容量を持たせる**。一覧の表示ずれを防げます。

### 表示と操作

7. **訪問回数による地図の濃淡**。`loadAreaIndex()` が既に回数を返しているため、
   `AreaMap` の色指定を段階分けするだけで実装できます。
8. **地図の拡大・移動**。市区町村の地図と場所選択の地図を拡大できるようにすると、
   点が密集する地域でも選びやすく、地図選択の精度も上がります。
9. **活動履歴の絞り込みと既読**。人数が増えると流れが速くなるため、
   「自分以外の動き」「前回見たあと」といった絞り込みがあると読みやすくなります。

### 運用

10. **RLS テストを CI で回す**。`./scripts/verify-rls.sh` は PostgreSQL があれば動くため、
    GitHub Actions に載せると、ポリシーの変更で公開範囲が壊れたときに気付けます。
